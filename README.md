# 배포 검증 워처 (deploy-watcher)

1. **무슨 주제인가** — 여러 웹사이트를 운영하다 보면 배포(새 버전 업로드) 후에 "진짜 반영됐는지"를 매번 손으로 확인하게 됩니다.
2. **무엇이 문제였나** — 서버가 정상(HTTP 200)이라고 답해도, 실제로는 캐시가 옛 버전을 보여주거나 페이지 내용이 깨져 있는 **"거짓 정상"** 상태가 있습니다. 이걸 사람이 일일이 잡아야 했습니다.
3. **그래서 무엇을 만들었나** — 사이트와 기대 조건을 등록하면 자동으로 감시하다가, 겉으로만 정상인 상태를 감지해 텔레그램으로 알려주는 작은 CLI 도구를 만들었습니다.

## 무엇을 자동화했나 (Before → After)

| 배포할 때마다 손으로 하던 일 | 워처 도입 후 |
|------|------|
| 브라우저 열고 사이트 하나하나 접속 | 등록만 해두면 자동 순찰 |
| 강력 새로고침·`?nc=` 붙여가며 "새 버전 맞나" 확인 | L3가 원본 vs 사용자 시점을 자동 비교 |
| 페이지 열어 내용 깨짐을 눈으로 확인 | L2 마커 검증 (렌더링 검증은 로드맵) |
| 문제가 생겨도 다음에 열어보기 전까지 모름 | 상태가 변하는 순간 텔레그램 알림 |

사이트가 1개면 손으로 해도 된다. 이 도구의 가치는 **사이트 수 × 배포 빈도**에 비례한다 — 여러 사이트를 소수 인원이 운영하는 곳(웹 에이전시 등)일수록 사람의 반복 확인이 통째로 사라진다.

## 감지 계층

| 층 | 검증 | 잡아내는 것 |
|----|------|------------|
| L1 생존 | HTTP 상태·응답시간 (총 시한·크기 상한 있는 실측) | 다운·지연 |
| L2 내용 | 페이지 안 필수 마커 실존 (인코딩 폴백 포함) | **200 거짓 양성** — 살아있는데 빈/에러 페이지 |
| L3 배포반영 | 캐시 우회(?nc) vs 사용자 시점 버전 비교 + 캐시 정책(max-age) 실측 | **배포했는데 옛 버전이 보이는 상태** |
| L4 렌더링 | 헤드리스 브라우저 실렌더 → JS 예외·렌더된 화면의 마커 검증 | **HTML은 오는데 화면이 깨진 상태** — JS 크래시, JS로만 그리는 페이지(SPA)의 내용 증발 |
| L5 보안 | ① 일반 방문자 vs 검색봇 시점 비교 ② Google Safe Browsing 등재 조회 | **해킹당했는데 주인만 모르는 상태** — 검색봇에만 보이는 도박 스팸(클로킹), 구글 위험 사이트 낙인 |

L5는 `security: true`로 켠다. 잡는 것과 못 잡는 것을 분명히 — 외부에서 보이는 침해 흔적은 잡지만, **서버 내부 파일 변조·웹쉘·공격 시도 탐지는 구조적으로 불가**하고(외부 관찰자는 자기가 유발한 응답만 본다), 진짜 검색봇 IP를 역방향 DNS로 검증하는 정교한 클로킹도 못 잡는다. 설계 근거·출처 = `docs/03-보안축-리서치.md`.

## 설치·실행

```bash
pip install -r requirements.txt

python -m watcher status                # 1회 점검, 읽기 전용 (알림·기록 없음)
python -m watcher once                  # 1회 점검 + 상태 전이 시 알림
python -m watcher watch --interval 300  # 주기 순찰 (기본 300초, 최소 5초)

# 배포 직후 집중 검증 — 15초 간격, 연속 3회 전 층 통과 시 "배포 안정" (결과 반드시 1회 보고)
python -m watcher deploy demo-shop --expect-version 1.0.2   # 기대 버전 앵커
python -m watcher deploy my-site --expect "여름세일"         # 서버를 못 만지는 빌더형 — 실화면 문구로 검증
```

앵커가 왜 필요한가: "원본=사용자 일치"만 보면 **배포가 서버에 아예 닿지 않아 둘 다 옛 버전**인 상태도 정상으로 보인다. `--expect-version`은 원본·사용자 모두 그 값일 때만 안정으로 판정한다.

**상태보드**: `watch`/`once`가 매 패스마다 `board.html` 한 장을 갱신한다 — 서버 없이 브라우저로 열기만 하면 되는 전 사이트 현황판 (15초 자동 새로고침, 최근 알림 이력 포함). `status`는 읽기 전용 계약이라 보드도 쓰지 않는다.

## 설정

`sites.json` — 감시 대상 (이 레포의 값이 실제 동작 예시):

```json
{
  "demo-shop": {
    "name": "데모샵",
    "url": "https://kidplayboi.github.io/deploy-watcher-demo/",
    "markers": ["데모샵", "장바구니"],
    "version_url": "https://kidplayboi.github.io/deploy-watcher-demo/version.txt",
    "timeout_sec": 10
  }
}
```

`markers` = 페이지에 반드시 있어야 할 텍스트. `version_url` = 배포 시 갱신하는 버전 파일(선택 — 없으면 L3 생략). `confirm_checks`(선택, 기본 1) = N회 연속 같은 관측일 때만 상태 확정(순단 플랩 방지 — 단 간헐 층(L4/L5)은 실관측 1회 + 승계로 확정된다). `render`(선택, 기본 false) = L4 렌더링 검증 — 무거워서 opt-in이며 Playwright 필요(`pip install playwright && python -m playwright install chromium`), `watch`에서는 `--render-every N`패스마다 1회(기본 5).

간헐 층의 대가(정직하게): `--render-every N`이면 L4를 안 돈 패스는 **직전 결과를 그대로 들고 간다**(모르는 것을 정상으로 치지 않기 위해). 그래서 L4 장애가 실제로 복구된 경우 🟢 통보가 최대 N주기(기본 5×5분=25분) 늦을 수 있다. 거짓 복구 알림을 없애는 대신 받아들인 트레이드오프다.

`security`(선택, 기본 false) = L5 보안 층 — 클로킹 비교 + Safe Browsing 조회(`GSB_API_KEY` 필요). `spam_keywords`(선택) = 기본 스팸 시그니처에 사이트별 문구 추가.

`.env` — `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`(텔레그램 알림), `GSB_API_KEY`(L5 평판 조회 — Google Cloud 콘솔에서 무료 발급). 형식은 `.env.example`. 텔레그램을 둘 다 비우면 콘솔 알림 **데모 모드**로 동작.

L5 클로킹을 직접 보려면 재현 서버로 확인할 수 있다 (해킹된 사이트를 흉내내 검색봇에게만 스팸을 보여준다):

```bash
python demo/cloaked_site.py     # http://127.0.0.1:8899
curl -s http://127.0.0.1:8899                        | grep 바카라   # 안 나옴
curl -s -A "Googlebot/2.1" http://127.0.0.1:8899     | grep 바카라   # 나옴
```

## 알림 정책

- 상태가 **변할 때만** 알림 (매 체크마다 울리면 알림 피로로 무시당함)
- 발송이 **성공한 뒤에만** 통보 상태를 갱신 — 전송 실패는 다음 패스에서 자동 재시도
- 통보 전에 스스로 복구된 순단은 버리지 않고 "이전 순단 사후 보고"로 1회 전달 (이탈 구간의 최악 사유 인용)
- 잘못 설정된 사이트는 경고 후 제외하고 나머지는 계속 감시 (가용성 우선)

## 알려진 한계 (정직하게)

- **클로킹 확정은 지연될 수 있다.** 요청마다 배너·문구가 바뀌는 페이지에서는 "유한 표본에서 안 보였다"가 결론이 될 수 없어, 여러 패스에 걸쳐 재현될 때만 🔴으로 확정한다(순증 6점 도달 시 — 관측이 없는 패스는 감쇠하므로 **경과 시간의 상한은 아니다**). 그 전에도 침묵하지 않고 🟠 "클로킹 의심 (n/6패스 확인 중)"으로 알린다. 회전이 없고 검색봇 표본 과반에서 재현되면 지연 없이 그 패스에서 확정한다
- **탐지 하한이 있다 — 검색봇에게 대략 13~14번에 1번 미만으로만 스팸을 보여주는 클로커는 🔴 확정까지 가지 않는다.** 확정이 순증 누적이라 "패스당 후보를 볼 확률 > 1/2"가 필요한데 봇 표본이 패스당 5~12회이기 때문이다. 실측(노출률 × 봇 시작 위상 전수 × 24패스): 1/6·1/10·1/12는 전 위상 확정 · 1/13은 12/13 위상 · 1/14는 2/14 · **1/15 이하는 0**. ⚠️그리고 하한 아래에서는 🟠에 머무는 것이 아니라, 봇 표본이 그 회차에 스팸을 못 보면 후보 자체가 안 생겨 **🟢으로 보고될 수 있다**(1/20에서 전 위상 평균 3.8%, 특정 시작 위상에서는 대부분의 패스). 하한을 낮추려면 봇 표본을 늘려야 하는데 그건 감시 대상 사이트의 부담과 직결돼 여기서 균형을 잡았다
- **클로킹 판정의 위상 보장은 확률적이다** — "절대 안 뚫린다"가 아니라 "패스가 쌓일수록 오탐 확률이 0에 수렴한다". 아래는 **실측 관측치이지 상한이 아니다**
  - 순차 회전(주기 2~24, 시작 위상 전수 × 6패스 = 1,206패스): 수리 전 하드 FAIL 86건 → 수리 후 0건. **다만 "0"은 그 표본의 관측치일 뿐이다** — 표본 수 뽑기 시드를 흔들면 주기 16에서 하드 FAIL이 재현된다(시드 16개 중 2개, 각 24패스에서 1~4회). 수리 전 대비 RED가 나는 조합이 9/180 → 2/180으로 줄었을 뿐 0이 아니다
  - 요청마다 무작위로 도박 문구가 끼는 페이지: 삽입 확률 5%·10%에서 3.4~4.1%/패스 → 관측 **0건**(각 800~1,800패스). 단 표본을 4배로 키우면 10%에서 0.03% 수준의 잔존이 관측된 적이 있다(외부 교차 게이트 실측) — **"0%"가 아니라 "이 표본에서 안 나왔다"로 읽어야 한다**
  - 삽입 확률 **30%에서는 1.17% → 0.33%가 남는다**(600패스). 응답 셋에 하나꼴로 도박 문구가 실리는 페이지는 이 도구의 관측 방식으로 클로킹과 완전히 가를 수 없다
- **의심 사이트에는 요청이 늘어난다** — 평시 클로킹 검사는 요청 2회지만, 후보가 잡히거나 추적 중인 사이트는 한 패스에 최대 29회(일반 5~16 + 검색봇 5~12)까지 쓴다. 확정된 사이트는 해소될 때까지 이 확장이 지속된다. 남의 사이트에 부담을 주는 구간이라 후보가 반증되는 즉시 조기 종료한다
- **CDN이 쿼리스트링을 캐시 키에서 무시**하도록 설정된 환경에서는 `?nc=` 캐시 우회가 무효 (GitHub Pages/Fastly는 쿼리를 캐시 키에 포함해 유효)
- **응답 헤더 단계에서 정체하는 병적 서버**는 닫을 핸들 자체가 없어 워커 회수가 **사실상 안 될 수 있음** (데몬 스레드라 프로세스 종료는 막지 않지만, 상시 순찰에서 이런 서버를 만날 때마다 스레드·소켓이 누적됨)
- **텔레그램 발송에는 총 시한이 없음** — 통제된 단일 API + 실패 시 상태 유지 재시도 구조로 수용한 트레이드오프
- **https 프록시 경유(TLS-in-TLS) 환경**에서는 소켓 강제 차단 API(shutdown)가 없어, 프레이밍 드리블형 병적 서버의 워커 회수가 안 될 수 있음 (정리 자체는 안전하게 close로 폴백)

(본문 트리클로 워커 회수가 안 되던 한계는 9~11차 게이트에서 수리됨 — 수신 즉시 반환 읽기(read1) + 시한 초과 시 소켓 강제 차단(urllib3 raw.shutdown() 위임). 바이트 드리블·chunked 프레이밍 드리블의 keep-alive/Connection: close 변종 모두 회귀 테스트로 고정)
