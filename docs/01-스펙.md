# 스펙 — 배포 검증 워처 (가칭 deploy-watcher)

> 2026-07-29 설계 문답으로 확정. 결정 근거 로그 = `ai-log/2026-07-29-03-설계문답.md`

## 3줄 인트로 (제출물 S5 초안)

1. **무슨 주제**: 여러 웹사이트를 운영하다 보면 배포(새 버전 업로드) 후에 "진짜 반영됐는지"를 매번 손으로 확인하게 된다.
2. **무엇이 문제**: 서버가 정상(200)이라고 답해도 실제로는 캐시가 옛 버전을 보여주거나, 화면이 자바스크립트 에러로 깨져 있는 경우가 있다 — 겉과 속이 다른 "거짓 정상"을 사람이 일일이 잡아야 했다.
3. **그래서 만든 것**: 사이트와 기대 조건을 등록하면 자동으로 감시하다가, 겉으로만 정상인 상태를 감지해 텔레그램으로 알려주는 작은 도구.

## 감지 4층 (깊이 = 차별화)

| 층 | 검증 | 잡아내는 것 |
|----|------|------------|
| L1 생존 | HTTP 상태·응답시간 | 서버 다운, 응답 지연 |
| L2 내용 | 페이지 내 필수 마커 존재 | **200 거짓양성** (살아있는데 빈 페이지/에러 페이지) |
| L3 배포반영 | 기대 버전 문자열 실측 (캐시 우회 요청) | **배포했는데 옛 버전이 보이는 상태** |
| L4 렌더링 | 헤드리스 브라우저로 실제 렌더 → JS 콘솔 에러·핵심 요소 존재 | **HTML은 오는데 화면이 깨진 상태** (프론트/백 버전 불일치 등) |

## 트리거 — 하이브리드

- **평시**: 5분 주기 순찰 (L1~L2 위주, L4는 주기 낮춤 — 무거우니까)
- **배포 직후**: `watch deploy <site>` 선언 시 집중 감시 모드 — 15초 간격 연속 체크, 연속 3회 전 층 정상이면 "배포 안정" 판정 후 평시 복귀
- 설계 근거: 배포 직후가 가장 위험한 시간대 (실사고 경험 기반)

## 알림 — 텔레그램, 상태 변화 시에만

- 정상→이상, 이상→정상 **전이 시에만** 발송 (매 체크마다 울리면 알림 피로 → 무시당함)
- 배포 집중 모드는 "안정 판정" / "검증 실패" 결과를 반드시 1회 보고

## 형태

- 코어: CLI (`add` / `watch` / `deploy` / `status`) + 설정 파일(사이트 목록·기대 조건)
- 선택(T4, 여유 시): 한 장짜리 상태 보드 — 소르테크 "통합관제" 미니어처
- 스택: Python (표준적·평가자 가독성) + Playwright(L4 헤드리스) + 텔레그램 Bot API(무료·직접 HTTP 호출)

## 타깃 서사 (회고용)

- **1차**: 웹 에이전시/제작사 — 소수 인원이 수십 개 고객사 사이트 운영. 가치 공식 = **사이트 수 × 배포 빈도**. 단일 도메인 개인에겐 과잉, 이 공식이 큰 조직일수록 필요
- **2차(확장)**: 제조기업 사내 시스템 통합관제 — "겉과 속이 다른 거짓 정상 감지"라는 문제의 산업 확장판

## 빌드 플랜

| 일차 | 작업 | 산출 |
|------|------|------|
| D1 | 코어: 설정→L1~L3 검증→텔레그램 알림 + 상태 전이 로직 | 동작하는 CLI |
| D2 | L4 렌더링 층 + 배포 집중 모드 + (여유 시) 상태 보드 · 실행 녹화 | 완성본 + 녹화 |
| D3 | AI 활용 기록·회고 정제 → docx/pdf · 요구사항 전 항목 크로스체크 | 제출 패키지 |
