# 스펙 — 배포 검증 워처 (가칭 deploy-watcher)

> 2026-07-29 설계 문답으로 확정. 결정 근거 로그 = `ai-log/2026-07-29-03-설계문답.md`

## 3줄 인트로 (제출물 S5 초안)

1. **무슨 주제**: 여러 웹사이트를 운영하다 보면 배포(새 버전 업로드) 후에 "진짜 반영됐는지"를 매번 손으로 확인하게 된다.
2. **무엇이 문제**: 서버가 정상(200)이라고 답해도 실제로는 캐시가 옛 버전을 보여주거나, 화면이 자바스크립트 에러로 깨져 있는 경우가 있다 — 겉과 속이 다른 "거짓 정상"을 사람이 일일이 잡아야 했다.
3. **그래서 만든 것**: 사이트와 기대 조건을 등록하면 자동으로 감시하다가, 겉으로만 정상인 상태를 감지해 텔레그램으로 알려주는 작은 도구.

## 포지셔닝 — 감지 전용, 배포는 하지 않는다

이 도구는 배포를 실행하지 않는다. **감시·검증 전용**이며, 이는 의도된 경계다:
- 배포 방법은 스택마다 다르다(git push·FTP·빌더 어드민 클릭) — 전부 해주려면 거대해진다. 반면 "잘 배포됐는지 확인"은 방문자처럼 밖에서 보면 되므로 **모든 스택에 통한다**
- 읽기 전용이라 고객 서버 권한·비밀번호가 불필요 → 에이전시가 고객사에 붙일 때 도입 장벽 0
- 배포하는 도구는 많지만, 배포 결과를 지켜봐주는 도구는 드물다 — 그 빈틈이 이 도구의 자리

**스택 무관 원칙**: L1(생존)·L2(내용)는 Node/PHP/아임웹/카페24 무엇이든 무설정 동작(순수 HTTP 관찰).
L3(배포반영)만 협조 수준에 따라 2모드:
| 모드 | 대상 | 방법 |
|------|------|------|
| 버전 모드 | 서버를 만질 수 있는 사이트 (Node·PHP·FTP 가능한 호스팅) | 배포 시 version.txt 한 줄 → 원본 vs 사용자 시점 비교 |
| 기대 마커 모드 | 빌더형 블랙박스 (아임웹 등 파일 업로드 불가) | 배포 시 `--expect "이번에 들어갈 문구"` 선언 → 실화면에 나타날 때까지 감시 |

## 감지 4층 (깊이 = 차별화)

| 층 | 검증 | 잡아내는 것 |
|----|------|------------|
| L1 생존 | HTTP 상태·응답시간 | 서버 다운, 응답 지연 |
| L2 내용 | 페이지 내 필수 마커 존재 | **200 거짓양성** (살아있는데 빈 페이지/에러 페이지) |
| L3 배포반영 | 기대 버전 문자열 실측 (캐시 우회 요청) | **배포했는데 옛 버전이 보이는 상태** |
| L4 렌더링 | 헤드리스 브라우저로 실제 렌더 → JS 콘솔 에러·핵심 요소 존재 | **HTML은 오는데 화면이 깨진 상태** (프론트/백 버전 불일치 등) |

## 트리거 — 하이브리드

- **평시**: 5분 주기 순찰 (L1~L2 위주, L4는 주기 낮춤 — 무거우니까)
- **배포 직후**: `watch deploy <site>` 선언 시 집중 감시 모드 — 15초 간격 연속 체크, 연속 3회 전 층 정상이면 "배포 안정" 판정 후 평시 복귀
- 설계 근거: 배포 직후가 가장 위험한 시간대 (실사고 경험 기반)

## 알림 — 텔레그램, 상태 변화 시에만

- 정상→이상, 이상→정상 **전이 시에만** 발송 (매 체크마다 울리면 알림 피로 → 무시당함)
- 배포 집중 모드는 "안정 판정" / "검증 실패" 결과를 반드시 1회 보고

## 형태

- 코어: CLI (`add` / `watch` / `deploy` / `status`) + 설정 파일(사이트 목록·기대 조건)
- 선택(T4, 여유 시): 한 장짜리 상태 보드 — 소르테크 "통합관제" 미니어처
- 스택: Python (표준적·평가자 가독성) + Playwright(L4 헤드리스) + 텔레그램 Bot API(무료·직접 HTTP 호출)

## 알림 문구 카탈로그

원칙: 한 문구에 3요소 — **어느 층(L1~L4) + 기대 vs 실측 + 조치 힌트**. 상태는 dot(🟢🟠🔴)+텍스트.

배포 집중 모드 (무소식 없음 — 성공/실패 반드시 1회 보고):
```
🚀 [데모샵] 배포 검증 시작 — 기대 v1.3, 15초 간격 집중 감시
🟢 [데모샵] 배포 안정 — v1.3 반영 확인, 4층 전부 통과 (47초 소요)
🟠 [데모샵] 배포 미반영 — 원본은 v1.3 갱신됨, 사용자 화면은 아직 v1.2 (CDN 캐시 추정, 최대 10분). 계속 감시
🔴 [데모샵] 배포 검증 실패 — 렌더링 에러(L4): TypeError: cart is undefined · 3회 연속. 롤백 검토 필요
```

평시 순찰 (상태 전이 시에만):
```
🔴 [데모샵] 이상 감지 — 응답은 200이지만 핵심 콘텐츠 없음(L2). 직전 정상 14:05
🟢 [데모샵] 회복 — 12분 만에 정상 복귀
```

## 데모 대상 + 녹화 시나리오

**감시 대상 = 과제용 데모 사이트** (GitHub Pages, 별도 공개 레포). 선정 근거:
① 우리 소유라 고장을 고의 재현 가능 ② GitHub Pages는 실제 CDN 캐시(~10분)가 있어 **L3 "배포했는데 옛 버전" 상황이 연출 없이 실재로 발생** ③ 개인정보·업무정보 무관, 평가자 재현 가능.
"원본(캐시 우회) vs 사용자 시점(캐시 경유)" 두 값을 다 실측해 간극을 보여주는 게 L3의 핵심. 안정 판정은 사용자 시점 기준.

녹화 씬 구성 (S4):
| 씬 | 조작 | 기대 알림 |
|----|------|----------|
| 1 | 정상 배포 → `watch deploy` | 🚀 시작 → 🟢 배포 안정 |
| 2 | 새 버전 배포 직후 (CDN 캐시 존속 중) | 🟠 배포 미반영 (원본 v1.3 / 사용자 v1.2) → 🟢 안정 |
| 3 | JS 에러 심은 배포 | 🔴 배포 검증 실패 (L4) |
| 4 | 평시 모드 중 콘텐츠 깨뜨림 → 복구 | 🔴 이상 감지 (L2) → 🟢 회복 |
| 5 | `status` 명령 | 전 사이트 현재 상태 한눈 요약 |

## 타깃 서사 (회고용)

- **1차**: 웹 에이전시/제작사 — 소수 인원이 수십 개 고객사 사이트 운영. 가치 공식 = **사이트 수 × 배포 빈도**. 단일 도메인 개인에겐 과잉, 이 공식이 큰 조직일수록 필요
- **2차(확장)**: 제조기업 사내 시스템 통합관제 — "겉과 속이 다른 거짓 정상 감지"라는 문제의 산업 확장판
