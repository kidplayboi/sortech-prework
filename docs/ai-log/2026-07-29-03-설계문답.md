# 2026-07-29 세션 03 — 설계 문답 (주제 확정)

**도구**: Claude Code (Claude Fable 5)

### [1] 주제 방향 교정 (사람 → AI)

**내가 시킨 것**: "취미가 아니라 이 회사에 나의 필요성을 입증하는 과제다. 나의 주관은 빼자. 나의 진짜 문제는 어디에 있고, 과제는 어디로 가야 하나. 짜치는 과제는 싫지만 시간도 밸런스 있게."
**AI가 답한 것**: "빼야 할 건 취미 주관, 남겨야 할 건 실제 겪은 업무 경험"으로 구분 — 과제 문서가 '본인의 진짜 문제'를 요구하므로 완전히 지우면 감점. 실제 반복 작업(여러 사이트 운영 중 배포 후 반영 확인) × 지원 회사 주력 도메인(통합관제) × 작은 스코프의 교집합으로 "배포 검증 워처" 제안. 짜침 방지 = 기능 개수가 아니라 판단의 깊이(200 거짓양성·캐시 우회·알림 피로)라고 정리.
**나의 대응**: 방향 수용. 단, 세부 설계(감지 범위·주기·트리거·타깃 기업)를 문답으로 같이 정하자고 역제안.

### [2] 설계 결정 4건 (일괄 문답)

AI가 각 축의 트레이드오프(시간 비용 포함)와 추천안을 깔고 질문 → 내가 결정:

| 축 | AI 추천 | 내 결정 | 비고 |
|----|---------|---------|------|
| 감지 깊이 | 3층 (생존+내용+배포반영) | **4층 (+렌더링 검증)** | AI 추천보다 한 층 깊게 — +반나절 비용 감수하고 완성도 선택 |
| 트리거 | 하이브리드 (평시 5분 + 배포 직후 집중) | 추천 수용 | "배포 직후가 가장 위험"이 설계 근거 |
| 형태 | CLI+텔레그램, 여유 시 상태보드 | 추천 수용 | 알림 도착 순간이 녹화 하이라이트 |
| 1차 타깃 | 웹 에이전시/제작사 | 추천 수용 | 가치 공식 = 사이트 수 × 배포 빈도 |
