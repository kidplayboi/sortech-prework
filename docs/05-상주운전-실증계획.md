# 상주 운전 오탐 실증 — 계획과 규칙

> 목적: "사이트 수 × 배포 빈도"라는 가치 주장과 "오탐을 막았다"는 설계 주장을 **감시 대상 1개 데모**가 아니라 **여러 실사이트 상주 운전 데이터**로 검증한다. 신규 기능은 만들지 않는다(스코프 확장 아님 — 기존 5층을 실전에 노출시키는 검증).

## 왜 필요한가

지금까지의 GREEN은 전부 ① 단위 테스트 ② 우리 소유 데모 1개다. 다음 질문에 아직 답이 없다:
- 남의 실사이트에서 L2 마커 검증이 오탐을 내는가 (동적 콘텐츠·A/B·지역 분기)
- L5 클로킹 비교가 정상 사이트를 침해로 오판하는가 (봇에게 다른 내용을 주는 정상 사례: 봇 차단 WAF·쿠키 배너·개인화)
- L4 렌더가 실제 무거운 사이트에서 몇 초 걸리고 콘솔 error가 얼마나 흔한가 (WARN 등급으로 내린 판단이 맞았나)
- 5분 주기 상주 운전이 몇 시간 뒤에도 스레드·메모리 누수 없이 도는가 (트리클 사가의 실전 확인)

## 대상 선정 규칙 (공개 레포 가드 준수)

- **공개된 오픈소스/공공 성격 사이트만** — 클라이언트·형 소유 사이트·업무 시스템은 절대 등록하지 않는다
- 읽기 전용 GET만 발생하며, 사이트당 5분 주기 = 하루 288회 수준(일반 크롤러보다 낮은 부하). robots.txt 상 접근 금지 경로는 쓰지 않고 루트만 본다
- **제출물에는 사이트를 익명화(사이트 A~L)해서 기록** — 남의 서비스 이름과 상태(특히 WARN/FAIL)를 공개 문서에 박지 않는다. 실제 URL은 로컬 `sites.local.json`에만 두고 깃 제외
- 마커는 각 사이트의 안정적인 문구(브랜드명 등)만 — 캠페인 문구처럼 자주 바뀌는 것은 그 자체가 오탐원

## 측정 항목

| 항목 | 방법 |
|------|------|
| 상태 분포 | 패스별 사이트 상태(OK/WARN/FAIL) 집계 — 층별 사유 상위 목록 |
| 오탐 판정 | WARN/FAIL이 난 건을 사람이 실제 확인 → 진짜 문제 / 오탐 분류 |
| L4 비용 | 렌더 소요 ms 분포, console.error 발생률(WARN 등급 결정의 검증) |
| L5 오탐 | 클로킹 WARN·FAIL 건의 실제 원인(봇 차단인가 침해인가) |
| 누수 | 장시간 운전 중 `watcher-*` 스레드 수·프로세스 메모리 추이 |
