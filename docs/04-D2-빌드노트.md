# D2 빌드노트 — 슬라이스별 설계 결정

> 슬라이스 순서: ① L4 렌더링 → ② deploy 집중 모드 → ③ 정적 상태보드 → ④ L5 보안 축 → 게이트 → 녹화

## 슬라이스 ① L4 렌더링 — "취소 불가 in-flight 작업" 정리 경로 선설계 (게이트 carryover 이행)

트리클 사가(9~12차)의 교훈 = L1~L3의 소켓 읽기는 **취소 불가능한 블로킹**이라 데몬 스레드 + 소켓 shutdown 위임이라는 우회가 필요했고, 그 우회가 4라운드에 걸쳐 벗겨졌다. L4는 같은 함정에 들어가지 않도록 **구조가 다른 도구를 다르게 다룬다**:

| 축 | L1~L3 (_bounded_get) | L4 (render.py) |
|----|---------------------|----------------|
| 블로킹 단위 | 소켓 read (취소 불가) | Playwright 작업 (자체 타임아웃 = **취소 가능**) |
| 시한 강제 | 데몬 워커 + join + shutdown 위임 | goto/wait 타임아웃 + try/finally `browser.close()` |
| 최악 시나리오 | 락에 갇힌 스레드 (프로세스 내 회수 불가 변종 존재) | 브라우저 = **별도 OS 프로세스** — close 실패해도 프로세스 kill로 회수 가능, 스레드 락 클래스 원천 부재 |
| 상주 여부 | 요청마다 새 커넥션 | **체크마다 launch/close** — 상주 브라우저는 크래시 누적·좀비 위험, L4는 저빈도라 launch 비용(수백 ms) 수용 |

판정 규칙 (spec L4 = "JS 콘솔 에러·핵심 요소 존재"):
- 페이지 로드 실패/타임아웃 → **FAIL**
- pageerror(잡히지 않은 JS 예외) ≥ 1 → **FAIL** (첫 에러를 detail에 — 알림 예: "TypeError: cart is undefined")
- 렌더된 본문에서 마커 부재 → **FAIL** (원본 HTML엔 없고 JS가 그리는 SPA 커버 — L2와의 차별점)
- console.error만 있는 경우 → **WARN** (서드파티 스크립트·광고가 흔히 유발 — 오탐으로 🔴 신뢰를 깎지 않는다)

운영 규칙:
- **opt-in**: 사이트 설정 `render: true`일 때만 (무겁고 Playwright 의존 — 기본 off)
- Playwright 미설치 + render:true → **조용한 통과 금지**(noop=실패 은폐 클래스) — "L4 검증 불가" WARN + 설치 안내
- `watch`는 N패스마다 1회(`--render-every`, 기본 5 — 평시 L1~L2 위주라는 스펙 트리거 설계), `once`/`status`는 매번, deploy 모드(슬라이스 ②)는 매 체크
- settle: `wait_until="load"` + 1초 고정 대기 후 판정. 렌더가 더 느린 SPA는 한계로 문서화 (기다림 휴리스틱을 쌓는 것보다 정직한 경계가 낫다)
